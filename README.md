# 💬 Krampus — мессенджер для учебной организации

**Krampus** — серверная часть мессенджера реального времени, написанная на **Go**.

Проект разработан как дипломная работа по специальности **09.02.07 Информационные системы и программирование**.

Система предназначена для учебной организации и заменяет заблокированные или недоступные мессенджеры для студентов и преподавателей. Krampus обеспечивает обмен сообщениями в реальном времени, групповые чаты, голосовые звонки и хранение данных в единой инфраструктуре.

---

## 📌 Назначение проекта

Приложение предназначено для учебной организации и позволяет:

- студентам и преподавателям обмениваться сообщениями в реальном времени;
- создавать личные и групповые чаты, а также каналы внутри групп;
- проводить групповые голосовые и видеозвонки (WebRTC);
- хранить переписку и пользовательские данные в единой базе данных;
- искать сообщения и пользователей;
- модерировать общение (бан, мьют) и вести аудит действий.

## ✅ Основные возможности

- регистрация и авторизация пользователя (JWT);
- личные сообщения и групповые чаты;
- каналы внутри группы;
- доставка сообщений в реальном времени через WebSocket;
- односторонний поток событий через SSE с дозагрузкой пропусков по `Last-Event-ID`;

- полнотекстовый поиск сообщений;
- модерация: бан, мьют, теневой бан;
- аудит действий пользователей;
- сжатие трафика (brotli / lz4 / zstd);
- наблюдаемость через стек Grafana / Loki / Tempo / Mimir.

## 🔄 Поток сообщения

1. Клиент отправляет сообщение по WebSocket.
2. `MessageService` записывает его в PostgreSQL (через sqlc) и публикует в Kafka (топик `incoming`).
3. Потребитель Kafka разносит сообщение подписчикам: индексатору поиска, потребителю аудита и рассыльщику WebSocket.
4. Подписанные клиенты получают сообщение в реальном времени.

## ⚙️ Архитектура

Внутренние модули следуют единой слоистой структуре:

```text
internal/<module>/
  domain/     — сущности, интерфейсы
  service/    — бизнес-логика
  storage/    — адаптеры БД / кэша
  adapters/   — HTTP-обработчики, WebSocket, SSE
```

Транспортный слой:

- **REST API** через Gin по адресу `/api/v1` (маршруты авторизации — без аутентификации, маршруты чатов — за `AuthMiddleware`);
- **WebSocket** по адресу `/ws` — рассылка через потребителя Kafka;
- **SSE** по адресу `/sse` — односторонний поток на комнату с дозагрузкой пропусков по `Last-Event-ID`.

## 🚀 Запуск проекта локально и тестирование

Это основной раздел для проверки работоспособности. Весь стек поднимается одной командой через Docker Compose.

### Требования

- [Docker](https://www.docker.com/) и Docker Compose (плагин `docker compose`)
- ~4 ГБ свободной оперативной памяти (поднимается Postgres, Redis, Kafka, MinIO и др.)
- Браузер с поддержкой WebRTC (Chrome / Firefox) — для проверки звонков

> Локально занятые порты `5432`, `6379`, `9000`, `9001` обходятся: Postgres публикуется на `5433`, Redis — на `6380`, MinIO — на `9100`/`9101`. Внутри сети Compose сервисы общаются по внутренним портам.

### Шаг 1. Подготовить файл окружения

```bash
cp .env.example .env
```

Значения по умолчанию рассчитаны на работу через Docker Compose «из коробки» — править `.env` для локального запуска не обязательно.

### Шаг 2. Поднять весь стек

```bash
docker compose up -d --build
```

Будут запущены следующие сервисы:

| Сервис | Адрес | Назначение |
|---|---|---|
| `frontend` | http://localhost:3000 | Веб-клиент (Nuxt 3) |
| `app` | http://localhost:8080 | Бэкенд (REST + WebSocket + SSE) |
| `call` | ws://localhost:8090 | Сервер сигналинга звонков |
| `postgres` | localhost:5433 | База данных |
| `redis` | localhost:6380 | Кэш и сессии |
| `kafka` | localhost:9092 | Транспорт сообщений |
| `minio` | http://localhost:9100 (консоль `:9101`) | Хранилище медиа |

### Шаг 3. Дождаться готовности

Первый запуск занимает несколько минут: собираются образы и проходят healthcheck-и Postgres, Kafka и MinIO. Проверить состояние:

```bash
docker compose ps
```

Все сервисы должны быть в состоянии `running` / `healthy`.

### Шаг 4. Открыть приложение

Открыть в браузере: **http://localhost:3000**

### Шаг 5. Тестовый сценарий

1. Открыть http://localhost:3000 и **зарегистрировать первого пользователя**.
2. Открыть **второе окно в режиме инкогнито** (авторизация хранится в `localStorage`, поэтому для второго аккаунта нужен отдельный профиль браузера) и зарегистрировать второго пользователя.
3. Создать группу, добавить второго пользователя, создать канал.
4. Отправить сообщения в обе стороны — они должны приходить в реальном времени.
5. Загрузить аватар в настройках профиля и аватар группы — они должны отображаться у обоих пользователей.

### Шаг 6. Проверка звонков (WebRTC)

> ⚠️ Звонкам обязательно требуется доступ к **микрофону**. Если разрешение не выдано, подключение прерывается и собеседники не видят друг друга.

1. В каждом окне браузера разрешить доступ к микрофону для `localhost:3000`.
2. Первый пользователь заходит в голосовой канал — он ожидает подключения (`count: 0` → `startCall`).
3. Второй пользователь заходит в тот же канал (`count: 1` → `connectionCall`) и подключается к первому.
4. У обоих появляются тайлы участников, работают кнопки микрофона, звука и стрима.

Подробности по звонкам: см. [front/CALL.md](front/CALL.md).

### Остановка

```bash
docker compose down        # остановить контейнеры
docker compose down -v     # остановить и удалить тома (полный сброс данных)
```

## 📞 Звонки и WebRTC

В рамках платформы реализована возможность создания аудио- и видеозвонков в реальном времени. На данный момент доступны только групповые звонки, однако существующая архитектура позволяет в дальнейшем преобразовать их в частные.

### Технические характеристики

- **Топология связи:** каждый с каждым (full mesh, P2P).
- **Технологии:** WebRTC, WebSocket, TypeScript, Go.
- **Сервер сигналинга:** отдельный Go-сервис (`front/server/api/main.go`), порт **8090**.
- **Предельная нагрузка:** локально протестировано до 6 одновременных пользователей, после чего начинается упор в производительность компьютера.

### Из чего состоит подсистема звонков

| Компонент | Путь | Назначение |
|---|---|---|
| Сервер сигналинга | `front/server/api/main.go` | WebSocket-реле: рассылает сообщения сигналинга между участниками комнаты |
| WebRTC-логика | `front/app/composabels/WebRTC.ts` | Установка `RTCPeerConnection`, обмен offer/answer/ICE |
| Сигналинг-клиент | `front/app/composabels/Signaling.ts` | Формирование и отправка сигнальных сообщений |
| UI звонка | `front/app/components/mainAreaChat/Voice.vue` | Вход в канал, тайлы участников, кнопки управления |
| Стор звонка | `front/app/stores/` (Pinia `Call`) | Состояние участников, `peerConnectionUsers` |

### Как устанавливается соединение

1. Пользователь заходит в голосовой канал — клиент открывает WebSocket к серверу сигналинга:
   `ws://localhost:8090/ws/<idRoom>/call`.
2. Клиент отправляет рукопожатие `{ type: "checkCountUserCall", id: <userId> }`.
3. Сервер отвечает количеством уже подключённых участников (без самого себя):
   - `count: 0` → пользователь один → `startCall()` (ждёт подключений);
   - `count > 0` → есть участники → `connectionCall()` (подключается к ним).
4. Дальше клиенты обмениваются `offer` / `answer` / `iceCandidate` через сервер-реле, и между ними устанавливается прямое P2P-соединение.

### ⚠️ Обязательное условие — доступ к микрофону

Перед установкой соединения вызывается `navigator.mediaDevices.getUserMedia({ audio: true })`.
**Если доступ к микрофону не выдан, вызов прерывается с исключением, рукопожатие не завершается и участники не видят друг друга.**

Поэтому при тестировании в каждом окне браузера нужно **разрешить доступ к микрофону** для `localhost:3000`.

### Запуск сервера сигналинга

Через Docker Compose сервер поднимается автоматически как сервис `call`. Перезапустить его (например, чтобы сбросить «зависших» клиентов в комнатах):

```bash
docker compose restart call
```

Вручную:

```bash
cd front/server/api
go run main.go
```

> Рекомендуется сначала запускать именно сервер сигналинга, а уже затем основной проект, чтобы избежать возможных ошибок при инициализации.

### Обоснование проектных решений

**Почему JSON, а не SDP в сигналинге.** В сигналинге используется JSON, так как в планах дальнейшего развития платформы предусмотрены функции, которые сложнее реализовать с использованием чистого SDP. Такой подход делает формат обмена более гибким и снижает количество ограничений при расширении платформы.

**Почему только P2P.** На текущем этапе реализована только P2P-модель, так как полноценное развёртывание тестовой инфраструктуры для SFU и MCU оказалось недоступным. Из-за этого их практическое тестирование пока не проводилось.

### Надёжность и устранение неполадок

Звонки в целом работают стабильно, однако в системе всё ещё присутствуют отдельные баги и временные решения. Если вы столкнулись с ошибкой:

- убедитесь, что выдан доступ к микрофону;
- перезапустите сервер сигналинга (`docker compose restart call`) — это сбрасывает «зависших» клиентов, из-за которых первый участник может ошибочно получить `count > 0`;
- выйдите из аккаунтов и войдите снова — на данный момент это основной способ временного устранения подобных проблем.

### STUN / TURN

Для установления соединения через NAT клиенту передаются STUN/TURN-серверы. По умолчанию используется публичный STUN Google (`stun:stun.l.google.com:19302`). Серверы настраиваются переменными окружения бэкенда (см. `.env.example`):

| Переменная | Назначение |
|---|---|
| `STUN_SERVERS` | Список STUN-серверов через запятую |
| `TURN_URL` | Адрес TURN-сервера (пусто — TURN отключён) |
| `TURN_USER` | Логин TURN |
| `TURN_PASS` | Пароль TURN |

Проверить работу STUN/TURN можно сервисом Trickle ICE:
[https://webrtc.github.io/samples/src/content/peerconnection/trickle-ice/](https://webrtc.github.io/samples/src/content/peerconnection/trickle-ice/)

Если всё работает корректно, в ответе должен появиться кандидат типа `srflx` (для STUN) или `relay` (для TURN).
